# Forerun

Your calendar knows *when* things happen. It has no idea what has to happen *before* them.
Forerun reads selected events, builds a deterministic prep ladder from a research-informed
playbook, and delivers a small number of specifically-worded notifications at the right lead
times — volunteers and leaders always contacted first.

- **Publisher:** Persue Apps LLC
- **Bundle id:** `com.persueapps.forerun`
- **Background task id:** `app.persue.forerun.refresh`
- **Platform:** iOS 26+, iPhone only in v1
- **Stack:** Swift 6 (strict concurrency = complete), SwiftUI, SwiftData, EventKit,
  UserNotifications, BackgroundTasks, Foundation Models, MessageUI, Contacts, App Intents
- **Cloud:** none. Everything is on-device. The only network code in the project is the
  optional, off-by-default TickTick OAuth source.

---

## The eight locked decisions

Do not re-litigate these mid-sprint. They are settled.

1. **The ladder is deterministic. The model only writes the sentence.** Timing, count,
   ordering, and gating are pure Swift. If the model is unavailable the app degrades to
   template copy and loses nothing structural.
2. **Volunteers and leaders are contacted before participants and students.** An engine
   invariant enforced in code, not a preference the model can reorder.
3. **Hard cap of 5 notifications per event, 6 per day, across all events.** Over-notification
   is the failure mode that kills this category of app. The cap cannot be raised past 8.
4. **No streaks, no badges, no completion percentages, no points.** A prep step is pending,
   done, snoozed, or skipped. Skipped costs nothing.
5. **Not a to-do list.** The Today screen shows what's due and stops. No inbox zero, no
   clearing ritual, no red count badge on the app icon — ever.
6. **Permissions are contextual.** Calendar when the user taps "Connect a calendar."
   Notifications when they save their first plan. Contacts when they first tap a leader.
7. **User edits are sticky.** Once a human edits a step's time or copy, regeneration never
   overwrites it.
8. **`IntelligenceProvider` from day one.** Foundation Models is one conformance. A
   server-backed one could be swapped in later without touching the engine.

### The rule for every change

> If a decision affects **when** something fires or **whether** it fires, it lives in Swift.
> If it affects **what the sentence says**, it can live in the model.

Engine logic is never generated by the model at runtime, and `phrase()` output is timing-inert —
it only ever reaches `PrepStep.generatedCopy`.

**Stated precisely:** *given a kind, the ladder is fully deterministic.* Classification is the one
place the model has influence, because the kind selects the playbook, and playbooks differ in
their offsets, their step count and their audiences. That is deliberate and is drawn in the
architecture diagram above — but it does mean "the model changes nothing about timing" would be
an overstatement, and that a device with no Apple Intelligence can classify an event differently
from one that has it. What the heuristic fallback guarantees is a *complete, correctly ordered
ladder*, not an identical one.

## Architecture

```
Sources (read-only)          EventKitSource · TickTickSource (optional)
        │  NormalizedEvent
        ▼
TrackingRules                colorFamily · calendar allowlist · manual override
        │  TrackedEvent
        ▼
Classifier                   IntelligenceProvider.classify() → EventKind
                             (falls back to keyword heuristics)
        ▼
PrepPlanBuilder              100% deterministic: playbook + lead time + budget + quiet hours
                             → PlanDraft with absolute fire dates
        ▼
Phraser                      IntelligenceProvider.phrase() → notification body
                             (validated, falls back to template string)
        ▼
NotificationScheduler        rolling 14-day window, < 50 pending requests
```

### Module layout

| Path | Contains | Depends on |
|---|---|---|
| `Packages/ForerunCore` | models, domain types, playbooks, engine, heuristics, validator | Foundation, SwiftData only |
| `Forerun/Sources` | `EventKitSource`, `TickTickSource` | EventKit, network |
| `Forerun/Intelligence` | `FoundationModelsProvider`, `ProviderResolver` | FoundationModels |
| `Forerun/Notifications` | `NotificationScheduler`, delegate, background refresh | UserNotifications, BackgroundTasks |
| `Forerun/Views` | Today, Upcoming, Events, Plan, Settings | SwiftUI |
| `Forerun/DesignSystem` | palette (light+dark), type ramp, containers, timeline rail | SwiftUI |

`ForerunCore` imports **no** SwiftUI, **no** EventKit, **no** FoundationModels, and no
networking. That is what makes the engine testable with `swift test` on macOS with no
simulator in the loop. Keep it that way.

## Engine invariants

`PrepPlanBuilder` enforces all ten. Each has a named unit test in
`Tests/ForerunCoreTests/EngineInvariantTests.swift`. There is no eleventh invariant in v1 —
an eleventh is a v1.1 request.

1. No step fires in the past. If the event is closer than the first offset, **compress**:
   scale remaining offsets proportionally into the available window and set `wasCompressed`.
2. **Audience ordering.** In any plan containing both a leader/volunteer step and a
   participant/student step, every leader step **in the run-up** fires strictly before every
   participant step in the run-up. If compression would violate this, participant steps are
   dropped, never reordered.

   *Post-event steps are excluded from both sides.* The volunteer playbook ends with a +1d
   "thank your leads" step; counting it would make it the latest leader step in every plan,
   which would make every participant step look out of order and silently delete the −24h
   "message the students" rung from every single team event. The invariant is about the
   sequence of the ask, not about follow-ups.
3. Cap at `maxStepsPerEvent`. Non-core steps drop first, latest-offset first.
4. Never fire inside quiet hours — shift forward to `preferredDeliveryHour`.
5. Never fire while another tracked event is in progress.
6. If the daily budget is exceeded, defer the lowest-priority step to the next available day
   *earlier* than the event, never later.
7. Two steps for the same event never fire within 4 hours of each other. Compression never
   goes below that gap — it drops steps instead.
8. Steps with `userPinnedTime` are exempt from 2, 4, 5, 6, and 7. A pin is a human decision,
   and it is the **only** thing in the app that can reorder audiences — locked decision 2 is
   about the model not reordering them, not about the user. Because nothing ever moves a leader
   step *earlier* to compensate, a pinned participant step genuinely can sit in front of the
   whole leader sequence; the Plan screen flags that rather than silently discarding the pin.
9. All-day events anchor to `preferredDeliveryHour` on their date.
10. Offsets are stored as intervals and fire dates are computed in the user's current
    calendar. Plans recompute on `NSSystemTimeZoneDidChange`.

## Design system

Warm editorial, not productivity-app cold.

| Token | Value | Use |
|---|---|---|
| paper | `#FBF7F0` | app background |
| ink | `#241F1A` | primary text |
| amber | `#C77D33` | accent, tracked rail, leaders |
| muted | `#8A8078` | secondary text |
| hairline | `#E8E0D5` | rules, rails, dividers |
| clay | `#9B5C4A` | participants / students |
| graphite | `#5A5550` | self |

- **Type:** New York (serif) for screen titles and event names. SF Pro Text for body and
  notification copy. One weight step between levels, no more.
- **Layout:** generous vertical rhythm, 20pt horizontal margins, no cards-within-cards. A prep
  ladder is a vertical timeline with a hairline rail, not a list of boxes.
- **Motion:** state changes only. No decorative animation.
- **Empty states:** a sentence, not an illustration.
- **Screens:** Today, Upcoming, Events, Plan. Settings behind a gear. That is the whole app.

### Containers

The three tab screens are a **container** layout: cards on a deeper field (`paperSunk`), where size
and elevation carry meaning rather than decoration. Plan and the sheets stay flat on `paper`.

- "No cards within cards" holds in the narrower form: **a container never contains another
  container.** Inside a card, grouping is hairlines and the tinted footer band.
- Elevation is `.container(surface:radius:elevation:)`. In light it is shadow; in dark a shadow is
  invisible, so the same case resolves to surface lift plus a lit top edge. Call sites never know
  which mode they are in.
- Every shadow is **warm ink**, never grey or black. Grey reads as a productivity dashboard.
- Additional tokens: `paperLift`, `hairlineSoft`, `footerTint`, `dotSpent`, `dateOutside`,
  `chevron`. Every token is dynamic — one `UIColor` resolving light or dark, with the SwiftUI
  `Color` derived from it, so the UIKit appearance proxy can never drift from the views.
- **Rung dots** (`RungDots`) show what is *left* of a ladder and empty as you work. They are a
  countdown, never a bar that fills toward a finished state — decision 4 rules out completion
  percentages, and a gauge that fills is the same idea wearing dots.

## Working agreements

- Swift 6 language mode, `SWIFT_STRICT_CONCURRENCY=complete`. Zero warnings at the gate.
- No force-unwraps in model or engine code.
- Every engine invariant gets a named test. Test names read as sentences.
- Never write an app icon badge (`setBadgeCount`). Decision 5.
- Never set `DEVELOPMENT_TEAM` or `CODE_SIGN_STYLE` to empty when regenerating the project.
- Schema is versioned from the first commit. Once a build has shipped to anyone, any model
  change is a new `VersionedSchema` plus a migration stage, not an edit to the current one.
  Before the first ship the schema is treated as still being drafted, and the version identifier
  is bumped to say so rather than left lying about the models.
- Practitioner conventions (volunteer lead times, leaders-before-participants) are labeled
  "recommended" in the UI. Only the strong-evidence items may be described as research-backed,
  and never as "proven."
